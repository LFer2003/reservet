# Reservet: руководство по обучению и реализации

[Español](../GUIA_JUNIOR.md) · [English](../en/JUNIOR_GUIDE.md) · **Русский**

**Техническое задание:** объём работы, подготовка без Docker и сдача в вашем GitHub
описаны в [главном README](../../README.ru.md). Этот документ — расширенный учебный
план: Docker, бронирования и SQS ниже не обязательны для задания. Вход в систему
обязателен согласно README.

Прочитайте также [правила работы над проектом](../../CONTRIBUTING.ru.md) и
[архитектурные соглашения](ARCHITECTURE.md). Перед сдачей запускайте `npm run check`.

## 1. Что мы создаём

Приложение для сотрудников ресторана: управление столиками, бронированиями и
уведомлениями клиентов. Сначала создадим API, затем подключим интерфейс, а потом
вынесем уведомления в отдельный воркер с SQS. Для первых этапов аккаунт AWS не нужен.

Начальная цель — понять весь путь запроса от HTTP до PostgreSQL. Конечная цель —
объяснить поведение системы при конкурентных запросах, повторных сообщениях и
сбоях внешних сервисов. Работайте небольшими шагами: сначала опишите ожидаемое
поведение, затем покажите успешные и ошибочные сценарии. Фиксированных сроков
нет: переходите дальше, когда сможете объяснить предыдущий этап.

## 2. Инструменты и начальные знания

Используем TypeScript для проверки типов, Express для HTTP, PostgreSQL для
хранения данных и Docker Compose для воспроизводимой базы разработки.

До первого задания изучите переменные, функции, объекты, массивы, промисы,
`async/await`, `try/catch`, модули и типы TypeScript. Разберитесь в GET, POST,
PATCH, JSON и кодах HTTP 200, 201, 400, 404, 409 и 500. В Git практикуйте
`status`, `diff`, ветки и небольшие коммиты. Не добавляйте `.env` в репозиторий.

## 3. Подготовка компьютера

1. Установите совместимый Node.js (не ниже 22.13), Git и редактор, например VS Code.
2. Установите [Docker Desktop для Windows](https://docs.docker.com/desktop/setup/install/windows-install/).
   Выполните требования WSL 2 и виртуализации. Могут потребоваться права
   администратора и перезагрузка Windows. Откройте Docker Desktop и выберите
   контейнеры Linux.
3. Откройте PowerShell в папке проекта и проверьте:

```powershell
node --version
npm --version
git --version
docker --version
docker compose version
docker info
```

Docker Desktop включает Compose. Если команда после установки не найдена,
откройте новый терминал. `docker info` должен подключаться к движку Docker.

## 4. Установка и первый запуск

Выполните команды по порядку из корня проекта:

```powershell
cd E:\reservet
npm ci
# Копируйте, только если .env ещё не существует:
Copy-Item .env.example .env
npm run db:up
npm run db:migrate
npm run dev
```

`npm ci` устанавливает версии из lock-файла. `.env` задаёт настройки сервера и
подключения. `db:up` скачивает PostgreSQL 17 и ожидает его готовности.
`db:migrate` создаёт схему. `dev` запускает сервер и перезапускает его при
редактировании. Локальный порт базы — **5433**, порт внутри контейнера — 5432.

В другом терминале:

```powershell
Invoke-RestMethod http://localhost:3000/health
Invoke-RestMethod http://localhost:3000/health/db
```

Первый запрос возвращает `status: ok`, второй должен вернуть
`database: connected`. Они проверяют процесс и подключение, но не наличие всех
таблиц. Отдельно проверьте миграцию:

```powershell
docker compose exec db psql -U reservet -d reservet -c "SELECT * FROM schema_migrations;"
docker compose exec db psql -U reservet -d reservet -c "SELECT * FROM restaurant_tables;"
```

Должна появиться запись `001_create_restaurant_tables.sql`, а список столиков
пока будет пустым. Снова запустите `npm run db:migrate`: исполнитель должен
сообщить, что миграция уже применена.

В следующих сеансах используйте `npm run db:up` и `npm run dev`; запускайте
миграции при появлении новых файлов. API останавливается через Ctrl+C, база —
командой `npm run db:down`. Том сохраняет данные. Не используйте
`docker compose down -v`, если не намерены удалить всю локальную базу.

Если PostgreSQL уже установлен, создайте свою базу и пользователя, настройте
`DATABASE_URL` в `.env` и пропустите команды Docker. Миграции остаются теми же.

## 5. Структура проекта

```text
src/
  server.ts                 Запуск и завершение процесса
  app.ts                    Express и маршруты состояния
  shared/config.ts          Проверка конфигурации при запуске
  shared/database.ts        Пул подключений
  modules/tables/           Здесь реализуется модуль столиков
public/                     Интерфейс и переводы
scripts/migrate.ts          Исполнитель неприменённых SQL-миграций
migrations/                 Версионируемые изменения схемы
compose.yaml                Локальная PostgreSQL с постоянным томом
```

Начинаем с модульного монолита: одно приложение, разделённое по бизнес-функциям.
Для столиков используйте следующий путь:

```text
Запрос → маршрут/контроллер → сервис → репозиторий → PostgreSQL
```

Маршрут интерпретирует HTTP и возвращает коды. Сервис выражает бизнес-правила.
Репозиторий выполняет SQL с параметрами (`$1`, `$2`), не объединяя запрос с
пользовательскими строками. Не создавайте дополнительные интерфейсы и слои без
понятной необходимости.

## 6. Миграции: изменение базы

Миграция — версионируемое изменение схемы. Первая создаёт `restaurant_tables`:
идентификатор, уникальное название, вместимость от 1 до 20, статус и время
создания. Ограничения защищают базу и от некорректных записей других программ.

Чтобы добавить поле, создайте новый файл, например
`migrations/002_add_table_location.sql`, с нужным `ALTER TABLE`. Выполните
`npm run db:migrate` и проверьте результат через `psql`. Не изменяйте применённую
миграцию: исполнитель сохраняет её имя и повторно её не запускает. Используйте
последовательную нумерацию с ведущими нулями.

Каждый файл выполняется в транзакции: при ошибке изменения этого файла
откатываются, запись о применении не создаётся. Предыдущие миграции сохраняются.
Блокировка предотвращает одновременную работу двух исполнителей. Не добавляйте
собственные `BEGIN`/`COMMIT` и операции, несовместимые с транзакцией, например
`CREATE INDEX CONCURRENTLY`. Автоматической обратной миграции нет: исправляйте
схему новой миграцией. Для производственной среды нужны также резервные копии и
совместимая стратегия развёртывания.

## 7. Первое задание: API столиков

**Изучить:** маршруты, проверку данных во время выполнения, SQL, ошибки и разделение ответственности.

1. Прочитайте `src/app.ts`, `database.ts` и миграцию. Объясните их связь.
2. Создайте `tables.repository.ts`: получение списка и добавление столика с
   параметризованным SQL.
3. Создайте `tables.service.ts`: проверка непустого названия до 80 символов,
   целой вместимости от 1 до 20 и допустимых статусов. TypeScript не проверяет
   входящий JSON.
4. Создайте `tables.routes.ts`, экспортируйте Router и подключите его в `app.ts`
   **до** обработчика 404.
5. Реализуйте `GET /api/tables` и `POST /api/tables`.
6. Добавьте `PATCH /api/tables/:id/status` для изменения статуса.

Контракт: GET возвращает массив и 200. POST получает
`{ "name": "Столик 1", "capacity": 4 }` и возвращает созданный столик с 201 и
статусом `available`. PATCH получает `{ "status": "occupied" }` и возвращает
обновлённый столик с 200. Статусы: `available`, `occupied`, `out_of_service`.
Некорректные данные — 400; столик не найден — 404; повторяющееся название — 409.
Преобразуйте ошибку PostgreSQL `23505` в конфликт и не раскрывайте внутренние
сообщения SQL. Проверяйте также идентификатор.

Проверка после реализации эндпоинтов:

```powershell
Invoke-RestMethod http://localhost:3000/api/tables
$body = @{ name = 'Столик 1'; capacity = 4 } | ConvertTo-Json
Invoke-RestMethod http://localhost:3000/api/tables -Method Post -ContentType 'application/json; charset=utf-8' -Body ([System.Text.Encoding]::UTF8.GetBytes($body))
```

Передача UTF-8-байтов в последней команде сохраняет кириллицу и в Windows PowerShell.

**Критерии приёмки:** список, создание и изменение статуса работают; данные
сохраняются после перезапуска; дубликат возвращает 409; вместимость 0 и 21 и
пустое название отклоняются; отсутствующий столик возвращает 404. Добавьте тесты
контракта и сохранения данных, затем выполните `npm run check`.

## 8. Второе задание: подключить интерфейс сотрудника

**Изучить:** HTML, CSS, формы, события, `fetch`, состояния загрузки и ошибки.

Интерфейс уже находится в `public/index.html`, `public/styles.css` и
`public/app.js` и доступен через Express по адресу http://localhost:3000.
Дополнительная сборка не требуется. Запустите `npm run dev` для просмотра
демонстрации, даже если PostgreSQL ещё не готов. Фронтенд использует браузерный
JavaScript, бэкенд — TypeScript. Выберите русский язык в шапке.

1. В режиме **Демонстрация** создайте столик, измените статусы, попробуйте поиск
   и фильтр. Данные находятся в памяти и сбрасываются при перезагрузке; это не
   проверка бэкенда.
2. Откройте инструменты разработчика, вкладку «Сеть»/Network, и выберите
   **Мой локальный API**. Изучите `GET /api/tables`: сначала он вернёт 404,
   потому что его реализация — ваше первое задание.
3. Реализуйте GET из раздела 7 и нажмите **Обновить**. Должны появиться реальные
   данные или пустой зал, если столики ещё не созданы.
4. Реализуйте POST и попробуйте **Новый столик**. Ответ должен содержать объект
   столика с целым `id`, `name`, целой `capacity` и `status`.
5. Реализуйте PATCH и проверьте переключатели статуса. Ответ — весь обновлённый
   столик, а не только сообщение или код 204.
6. Перезагрузите страницу, снова выберите режим API и проверьте сохранение
   данных, в том числе напрямую в PostgreSQL.
7. Прочитайте `request`, `load`, `render` и `changeStatus` в `public/app.js`.
   Объясните разницу между проверкой браузера и обязательной проверкой сервера.

Режим API показывает сбои подключения, коды HTTP и несовместимые ответы. Он не
скрывает их демонстрационными столиками. Интерфейс не подключается к базе
напрямую. Вход в систему и защита серверных маршрутов остаются заданиями
начинающего разработчика: учебный экран не реализует аутентификацию.

**Критерии приёмки:** понятные ошибки, отсутствие повторных отправок во время
ожидания, управление клавиатурой и обновление представления после сохранения.
В режиме API данные сохраняются после перезагрузки.

## 9. Третье задание: бронирования и конкурентные запросы

**Изучить:** реляционную модель, внешние ключи, даты, транзакции и индексы.

Сначала определите правила. У бронирования есть столик, имя клиента, число
гостей, начало, конец и статус подтверждено/отменено. Храните моменты времени
в `timestamptz`, показывайте время в `America/Cancun`. Конец позже начала,
число гостей не превышает вместимость, активные бронирования не пересекаются.
Интервалы пересекаются, если `startA < endB` и `endA > startB`; соприкосновение
границ разрешено.

Создайте миграцию и эндпоинты создания, получения списка и отмены. Затем
смоделируйте два одновременных запроса на один столик. Проверка перед INSERT
без защиты позволяет обоим запросам увидеть свободное время.

Первое решение — транзакция, блокирующая строку столика через
`SELECT ... FOR UPDATE`, проверяющая доступность и добавляющая бронь. Все
операции, влияющие на доступность, должны соблюдать этот же порядок.
Прочитайте [документацию PostgreSQL о блокировках](https://www.postgresql.org/docs/17/explicit-locking.html).
Позже сравните это решение с ограничением исключения в базе данных.

**Критерии приёмки:** отмена освобождает интервал; два конкурентных пересекающихся
бронирования не могут быть подтверждены одновременно. Добавьте интеграционный
тест конкурентных запросов. Статус `occupied` отражает текущее обслуживание,
а не будущий календарь бронирований.

## 10. Четвёртое задание: уведомления через SQS

**Изучить:** отправителя, потребителя, очередь, сообщения и отдельные процессы.

Сначала реализуйте имитацию уведомления записью в консоль. Добавьте задержки и
сбои, чтобы увидеть последствия отправки внутри HTTP-запроса. Затем создайте
отдельный воркер и учебную очередь в локальном эмуляторе или в аккаунте AWS,
согласованном с наставником. Не храните секреты в коде.

API подтверждает бронь и подготавливает событие с `eventId`, `type`, `version`,
`occurredAt` и `reservationId`. Воркер получает сообщение, выполняет действие и
удаляет сообщение только после успеха. Настройте тайм-аут видимости с запасом
на обработку. Сверяйтесь с
[официальной документацией SQS](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/welcome.html).

**Критерии приёмки:** бронирования создаются при выключенном воркере; после
запуска он обрабатывает накопившиеся сообщения. API не ждёт отправки.
Сначала используйте имитацию, не отправляя сообщения реальным клиентам.

## 11. Пятое задание: сбои, дубликаты и outbox

**Изучить:** доставку как минимум один раз, идемпотентность, повторные попытки,
очередь недоставленных сообщений (DLQ) и согласованность в конечном счёте.

1. Обработайте событие дважды. Используйте `eventId` и постоянную запись для
   контроля дубликатов. Обсудите сбой между отправкой и записью результата:
   для более сильной гарантии внешний провайдер должен поддерживать ключ идемпотентности.
2. Смоделируйте временные сбои и проверьте повторные попытки.
3. Настройте DLQ с ограничением числа попыток. Вызовите постоянную ошибку,
   изучите сообщение и восстановите обработку после исправления причины.
4. Смоделируйте падение между сохранением брони и публикацией в SQS. Добавьте
   таблицу outbox: бронь и событие сохраняются в одной транзакции; отдельный
   издатель отправляет события и помечает их отправленными. Сбой после
   публикации может вызвать дубликат, поэтому идемпотентность всё ещё нужна.

**Критерии приёмки:** намерение уведомить о подтверждённой брони не теряется;
дубликаты обрабатываются; сообщение с ошибкой можно отследить и восстановить.

## 12. Следующие этапы

Лист ожидания: реагировать на отмену, не уведомляя нескольких людей
несогласованно. Роли: сотрудник и администратор с серверной авторизацией.
Аудит: кто изменил бронь. Наблюдаемость: идентификаторы запросов и событий,
метрики ошибок и возраста сообщений в очереди. CI: типы, сборка и тесты на
каждое изменение. Развёртывание: настройки окружений, секреты, управляемые
миграции и резервные копии.

Выделяйте сервис, только когда можете объяснить выгоду и затраты в эксплуатации,
сети и согласованности. Первый кандидат — воркер уведомлений.

## 13. Работа с наставником

Для каждого задания подготовьте описание проблемы, проектное решение,
небольшое изменение, демонстрацию и подтверждение проверки. Наставник проверяет
бизнес-правила, SQL, ошибки и понятность. Разработчик должен уметь объяснить код.

Полезные вопросы: что произойдёт при двух одновременных запросах? Если PostgreSQL
не отвечает? Если сообщение пришло дважды? Какие данные не должны попасть в лог?

## 14. Частые проблемы

| Симптом                      | Действие                                                                                                           |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `docker` не найден           | Установите Docker Desktop и откройте новый терминал.                                                               |
| Docker не подключается       | Откройте Desktop и проверьте `docker info`.                                                                        |
| Порт 5433 занят              | Опубликуйте `5434:5432` и поменяйте порт DATABASE_URL на 5434.                                                     |
| Нет DATABASE_URL             | Скопируйте `.env.example` в `.env` из корня проекта.                                                               |
| Подключение отклонено        | Выполните `db:up`, проверьте `docker compose ps` и `docker compose logs db`.                                       |
| Новые пароли не работают     | Переменные Compose инициализируют только новый том; сохраните исходные данные или измените пользователя через SQL. |
| Таблица отсутствует          | Выполните `db:migrate` с тем же DATABASE_URL, что у сервера.                                                       |
| Порт 3000 занят              | Измените PORT в `.env` и перезапустите сервер.                                                                     |
| `/api/tables` возвращает 404 | Это первое задание: эндпоинт ещё не реализован.                                                                    |

## 15. Исходное состояние

Подготовлены зависимости, конфигурация разработки, сервер состояния, Compose,
исполнитель миграций, схема столиков, интерфейс demo/API, инструменты качества и
автоматические тесты. Задания разработчика: API столиков, проверенная интеграция,
вход в систему, бронирования, бизнес-тесты и все этапы SQS.

Настройте собственную базу и DATABASE_URL под свою установку. Проверьте миграции
на локальной базе. Для задания следуйте объёму и подготовке без Docker из README;
бронирования и SQS — необязательные последующие учебные этапы.

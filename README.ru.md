# Reservet · Техническое задание для начинающего разработчика

[Español](README.md) · [English](README.en.md) · **Русский**

Доработайте приложение для сотрудников ресторана: **вход в систему, управление
столиками и хранение в PostgreSQL**. Работайте локально, опубликуйте решение
**в своём GitHub** и отправьте ссылку с воспроизводимыми инструкциями.

Этот README определяет обязательный объём работы. Срок сообщает проверяющий;
опишите незавершённые задачи. Дополнительные этапы учебных руководств не входят
в это техническое задание.

## 1. Исходное состояние и объём работы

Подготовлены TypeScript/Express, подключение и миграции PostgreSQL, схема столиков,
интерфейс на испанском, английском и русском с режимами demo/API и базовые тесты.

Реализуйте аутентификацию, защиту эндпоинтов столиков, список/создание/смену статуса,
подключите интерфейс, добавьте тесты и документацию. Входа в систему пока нет:
его нужно разработать.

**Docker, AWS/SQS, Cloudflare, раннер, домены и развёртывание не требуются.**
Бронирования, платежи, склад и восстановление пароля также не нужны.
Инфраструктурой исходного репозитория занимается проверяющий, а не кандидат.

## 2. Ваш репозиторий

Создайте пустой репозиторий в своём GitHub без дополнительного README. Сохраните
историю проекта и измените адрес отправки коммитов:

```powershell
git clone https://github.com/Eddierh/reservet.git reservet-assessment
cd reservet-assessment
git remote rename origin upstream
git remote add origin https://github.com/YOUR_USERNAME/reservet-technical-assessment.git
git push -u origin main
git switch -c feat/technical-test
```

Замените имя пользователя и репозитория своими. Делайте небольшие коммиты в своей
ветке. Не отправляйте изменения и PR в исходный репозиторий. Для закрытого
репозитория предоставьте проверяющему доступ перед сдачей.

## 3. Локальная подготовка без Docker

Установите Git, Node.js **22.13 или выше с учётом совместимости зависимостей** и
PostgreSQL **17** напрямую на компьютер. Проверьте `git --version`,
`node --version`, `npm --version`, `psql --version`. Если psql отсутствует в PATH,
используйте SQL Shell или инструмент запросов pgAdmin.

Подключитесь к локальному PostgreSQL как администратор и выполните команды
**по отдельности**, с включённым autocommit: CREATE DATABASE нельзя запускать
внутри транзакции.

```sql
CREATE ROLE reservet_candidate LOGIN PASSWORD 'local_candidate_password';
CREATE DATABASE reservet_candidate OWNER reservet_candidate;
CREATE DATABASE reservet_candidate_test OWNER reservet_candidate;
```

Если имена заняты, выберите другие. Пользователю приложения не нужны права
суперпользователя. База `_test` предназначена только для тестов. Не подключайтесь
к dev/pro исходного проекта.

```powershell
npm ci
# Только если .env ещё не существует:
Copy-Item .env.example .env
```

Настройте `.env` под свою установку:

```dotenv
PORT=3000
DATABASE_URL=postgresql://reservet_candidate:local_candidate_password@localhost:5432/reservet_candidate
```

Исходный пример использует **5433** для Docker; прямая установка PostgreSQL обычно
использует **5432**. Укажите реальный порт, специальные символы пароля кодируйте
для URL. Не добавляйте `.env` и реальные секреты в репозиторий.

```powershell
npm run db:migrate
npm run dev
```

Откройте **http://localhost:3000** и проверьте в другом терминале:

```powershell
Invoke-RestMethod http://localhost:3000/health
Invoke-RestMethod http://localhost:3000/health/db
```

Ожидаются `status: ok` и `database: connected`. Для проверки бэкенда выберите
**Мой локальный API**. Сначала `/api/tables` возвращает 404: его нужно реализовать.
Демонстрация хранит данные только в памяти и не подтверждает сохранение в БД.
Не используйте `npm run db:up` и `npm run db:down`: это команды Docker.

## 4. Обязательные задачи

### A. Аутентификация

- Добавьте миграции пользователей и повторяемый seed или процедуру создания
  тестового пользователя. Не храните реальные пароли в Git.
- Реализуйте вход, выход и получение текущей сессии. Выберите сессии или токены,
  объясните выбор, срок действия и поведение отзыва доступа при выходе.
- Хешируйте пароли через scrypt, bcrypt или Argon2; не используйте открытый текст
  и простой SHA-256. Неверный вход: 401 и общее сообщение об ошибке.
- Защитите **все эндпоинты столиков на сервере**: без аутентификации возвращайте 401. Скрытия кнопок интерфейса недостаточно.
- Создайте экран входа и действие выхода, сохранив три языка и переключатель.
  Публичная регистрация, почта и сложные роли не требуются.
- Опишите новые переменные примерами в `.env.example`. Маршруты состояния можно
  оставить публичными, без раскрытия секретов.

### B. API столиков

| Метод и маршрут                | Вход                                    | Результат                                      |
| ------------------------------ | --------------------------------------- | ---------------------------------------------- |
| `GET /api/tables`              | Без тела                                | 200 и массив столиков                          |
| `POST /api/tables`             | `{ "name": "Столик 1", "capacity": 4 }` | 201 и созданный столик со статусом `available` |
| `PATCH /api/tables/:id/status` | `{ "status": "occupied" }`              | 200 и полный обновлённый столик                |

Каждый столик содержит положительный целый `id`, `name`, целую `capacity` и
`status`. Проверяйте непустое название до 80 символов, вместимость **1–20**,
положительный ID и статусы `available`, `occupied`, `out_of_service`.

Некорректные данные — **400**, столик отсутствует — **404**, повторяющееся название —
**409**, нет аутентификации — **401**. Используйте параметры SQL и ограничения БД.
Не возвращайте клиенту запросы, пароли и стеки вызовов.

### C. Архитектура и интерфейс

- Разделите маршруты, сервисы и репозитории: HTTP, бизнес-правила и SQL имеют
  разную ответственность.
- Добавляйте новые миграции, не меняя применённые. Решение должно запускаться
  на пустой базе по документированным командам, без скрытых ручных изменений.
- Подключите список, форму, фильтры и смену статуса существующего интерфейса.
  Показывайте загрузку и ошибки, предотвращайте повторную отправку и безопасно
  отображайте внешний текст. Проверяйте данные на сервере независимо от браузера.
- Столики в режиме API должны сохраняться после перезагрузки страницы и сервера.
  Демонстрация не должна скрывать ошибки бэкенда.
- Для cookie сохраняйте один origin и опишите настройки безопасности.
- Поиск не должен зависеть от регистра; выбранный язык должен сохраняться после перезагрузки.

### D. Тесты и качество

Проверьте правильный/неправильный вход, запросы без сессии, выход согласно выбранному
механизму, создание/список/смену статуса, валидацию, дубликаты и отсутствующий столик.
Проверьте сохранение в базе `_test`, никогда не удаляя рабочие данные ради тестов.

Исходные тесты используют mocks/JSDOM и не покрывают ваш бизнес-бэкенд.
Опишите конфигурацию и миграции тестовой базы, команды и имитируемые части.
Если нужен `TEST_DATABASE_URL`, задокументируйте его и подготовьте временную БД
для интеграционных тестов в CI. Не отключайте существующие проверки.

```powershell
npm run format
npm run check
```

`check` запускает lint, форматирование, проверку типов, тесты и сборку.
**Verificaciones** должен успешно выполняться в вашем GitHub. Развёртывание
разрешено только исходному репозиторию и пропускается в копиях: раннер не нужен.

## 5. Порядок работы и публикация

1. Подготовьте PostgreSQL и проверьте `/health/db`.
2. Реализуйте и протестируйте столики в своей ветке.
3. Добавьте пользователей, seed, вход и защиту модуля.
4. Подключите интерфейс, проверьте три языка и завершите тесты.
5. Выполните проверки и повторите свои инструкции с нуля.
6. Отправьте ветку, создайте PR **в своём репозитории**, проверьте и объедините
   его в ветку по умолчанию, чтобы итоговое решение было легко найти.

```powershell
git add <изменённые-файлы>
git commit -m "feat: describe your implemented change"
git push -u origin feat/technical-test
```

## 6. Оценка

### Использование ИИ и объяснение решения

- **Разрешено использовать ИИ для программирования, исследования, отладки и тестов.**
  Укажите инструменты и части работы, где они помогли.
- Вы отвечаете за понимание, проверку и тестирование всего кода, включая
  сгенерированный. Не передавайте инструментам секреты и персональные данные.
- Письменно объясните путь вход → авторизованный запрос → сервис → PostgreSQL,
  свои решения и способ проверки результата.
- Опишите предложение ИИ, которое исправили или отклонили, и причину. Если такого
  не было, опишите решение, проверенное по документации или тестами.
- Полная история переписки не нужна. Объясняющее видео необязательно;
  **заданий на программирование и изменений кода вживую с проверяющим не будет**.

### Проверка исходного кода

В исходном коде могут быть функциональные дефекты. Их поиск и исправление входят
в задание. Исходные проверки не гарантируют правильность всех сценариев:
дополняйте тесты, не отключая существующие.

Не ограничивайтесь успешным сценарием: проверьте границы, ошибки и поведение
после перезагрузки. Для каждой проблемы опишите **симптом, воспроизведение,
причину, исправление и регрессионный тест**. Объясняйте доказательства, а не просто
сообщайте, что проблему исправил ИИ.

### Критерии

| Критерий         | Подтверждение                                                     |
| ---------------- | ----------------------------------------------------------------- |
| Функциональность | Вход и столики работают с реальным PostgreSQL                     |
| Дизайн           | Понятное разделение ответственности и объяснённые решения         |
| Безопасность     | Хеши паролей, защита сервера, валидация и параметры SQL           |
| Тесты            | Воспроизводимые успешные и ошибочные сценарии и сохранение данных |
| Сдача            | Понятные коммиты, успешный CI и полные инструкции                 |

Вы должны уметь объяснить код и использованные инструменты или помощь.
Бронирования, SQS, микросервисы и развёртывание не требуются и не заменяют
обязательные задачи.

## 7. Сдача проверяющему

Отправьте тем же способом, которым получили задание:

- **URL вашего репозитория**, доступного проверяющему, итоговую ветку и SHA коммита.
- Ссылку на PR вашего репозитория и успешный запуск CI.
- README с установкой, PostgreSQL, переменными, миграциями, seed, запуском
  приложения и командами всех наборов тестов.
- Данные **только локального демонстрационного пользователя** или процедуру их
  создания. Не отправляйте личные ключи и секреты других окружений.
- Решения, незавершённые задачи и ограничения. Скриншоты или видео необязательны
  и не заменяют код и инструкции.
- Раздел об использовании ИИ и список найденных проблем с объяснениями и новыми тестами.

```text
Репозиторий: https://github.com/YOUR_USERNAME/reservet-technical-assessment
Итоговая ветка и коммит:
Pull request:
CI:
Инструкции запуска: раздел моего README
Тестовый пользователь: описанная процедура seed
Готово / осталось:
```

Перед сдачей клонируйте свой репозиторий в другую папку и выполните собственные
инструкции. Проверка не должна зависеть от вашего `.env`, файлов вне репозитория
и доступа к нашему компьютеру.

# Как развёртывать собственные проекты

[Español](../DEPLOYMENT.md) · [English](../en/DEPLOYMENT.md) · **Русский**

Дополнительный учебный материал. **Развёртывание не входит в техническое задание**:
работайте локально и сдавайте свой репозиторий по [README](../../README.ru.md).

Все ресурсы для практики должны принадлежать **вашему проекту**: репозиторий,
аккаунт хостинга, база, секреты, домен и пайплайн. Это руководство не предоставляет
доступа и инструкций по управлению инфраструктурой проверяющего.

## 1. CI и развёртывание

**CI** устанавливает зависимости и проверяет формат, типы, тесты и сборку.
Достаточно раннера GitHub; свой сервер не нужен. **Развёртывание** публикует
проверенную версию на вашем хостинге и проверяет её работу. Для этого нужны
собственный ресурс и учётные данные. Успешный CI сам по себе не публикует
приложение и не проверяет подключение к рабочей базе.

## 2. Начните с CI своего репозитория

В проекте уже есть **Verificaciones**. Проверьте его запуск в своей копии при push
и PR. Для другого Node-проекта с такими же скриптами минимальный пример
`.github/workflows/ci.yml`:

```yaml
name: CI
on: [push, pull_request]
permissions:
  contents: read
jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '22'
          cache: npm
      - run: npm ci
      - run: npm run check
```

Адаптируйте версии и команды, сохраняйте lock-файл. Для интеграционных тестов с
PostgreSQL подготовьте отдельную временную базу CI. Не запускайте разрушающие
тесты на опубликованной базе.

## 3. Подготовьте собственный хостинг

Выберите свою платформу или сервер. Хостинга с Node.js может быть достаточно:
**Docker необязателен**. Настройте свой репозиторий и ветку, версию Node, рабочий
каталог, команды сборки (здесь `npm ci`, `npm run build`) и запуска (здесь
`npm start`). Создайте свою постоянную базу PostgreSQL.

Задайте переменные приложения: секрет `DATABASE_URL`, выделенный хостингом `PORT`,
при сетевом прослушивании — `HOST=0.0.0.0`. Реальные значения храните в защищённых
настройках хостинга или CI, не в Git, образах, скриншотах и логах. В `.env.example`
публикуйте имена переменных и примеры без реальных секретов.

## 4. Разделите тестовое и рабочее окружения

| Ресурс     | Тестовое окружение  | Продакшен                 |
| ---------- | ------------------- | ------------------------- |
| Приложение | Ваш тестовый сервис | Ваш опубликованный сервис |
| База       | Вымышленные данные  | Рабочие данные            |
| Секреты    | Только тестовые     | Только для продакшена     |
| URL        | Ваш тестовый адрес  | Ваш публичный адрес       |
| Публикация | Проверка изменений  | Проверенная версия        |

`develop`/`main` — возможное соглашение, не требование. GitHub environments позволяют
разделять секреты и ограничивать ветки; доступность функций зависит от тарифа и
видимости репозитория. Защитите важные ветки через PR и проверки, определите,
кто имеет право публиковать.

## 5. Определите последовательность публикации

Для **своего** пайплайна: выполните CI и остановитесь при ошибке; создайте артефакт
с SHA коммита; сохраните предыдущую версию и при необходимости резервную копию БД;
выполните миграции; запустите проверенную версию; проверьте состояние и типовую
операцию; запишите версию, результат и URL в своём репозитории.

Здесь миграции запускаются через `npm run db:migrate` и требуют зависимости
разработки `tsx`. Выполняйте их на release-этапе с установленными инструментами
или подготовьте скомпилированный исполнитель. Не рассчитывайте на наличие `tsx`
после установки только production-зависимостей.

Подключение и команда публикации зависят от вашего хостинга. Следуйте его
официальной документации и используйте минимальные права. Здесь нет готового
задания для чужого сервера. Создайте workflow под свои ресурсы; служебные файлы
исходного репозитория не являются шаблоном развёртывания вашего решения.

## 6. Проверка и восстановление

Проверьте `/`, `/health` и `/health/db` на своём URL. В логах не должны раскрываться
персональные данные и секреты. Проверьте сохранение после перезапуска и разделение
баз. До работы с реальными данными настройте HTTPS и аутентификацию.

Если используете туннель, создайте его в своём аккаунте и направьте только к своему
сервису. Туннель обеспечивает соединение, но не вход пользователей и не постоянную
доступность компьютера-источника.

При ошибке миграции остановите публикацию. Откат приложения не отменяет изменения
схемы автоматически. Проверяйте восстановление копий на временной базе и учитывайте
записи, сделанные после создания копии.

## 7. Документация своего проекта

Опишите требования, переменные без секретов, команды сборки/запуска/миграций,
проверки CI и тестов, окружения, свои URL, правила публикации, проверку,
восстановление, ограничения и владельца ресурсов.

Для технического задания достаточно результатов из README. Это руководство
поможет развивать **собственные проекты**, когда решите их публиковать.
